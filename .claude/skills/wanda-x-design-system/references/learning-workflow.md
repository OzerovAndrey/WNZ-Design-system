# Режим навчання — відстежуємо компоненти, які освіжає команда

Команда поступово освіжає й додає компоненти у Figma. Claude **лише читає** (Figma зараз read-only, правило 16), вивчає, як кожен компонент влаштований — характер, стани, токени, — і веде історію змін. Claude **нічого не виправляє і не «покращує»**: розбіжності з правилами записує як питання до команди.

Джерела знань, від надійнішого до менш надійного:
1. Що сказала команда (рішення) — записується без позначок.
2. Знімок компонента з файлу (`snapshots/<component>.json`) — факти структури.
3. Скриншот — як компонент виглядає в станах, MB/XON, Inverted.
4. Висновки Claude — позначати **(спостереження)**; призначення не вигадувати — якщо неочевидне, у «Відкриті питання».

## Тригери

| Фраза / ситуація | Що робити |
|---|---|
| «оновили / освіжили / доробили `<Компонент>`» (+ посилання або назва сторінки) | повний цикл нижче |
| «додали новий компонент `<X>`» | повний цикл; рядок у реєстрі з нуля |
| «що змінилось у `<X>`?» | кроки 1–2 + 4 (знімок і diff), без переписування доків |
| «вивчи сторінку `<Y>`» | цикл для кожного набору на сторінці |
| Початок будь-якої сесії Wanda X | після кроку зі свіжими токенами (правило 0) — спитати, які компоненти чіпали з минулого разу; підказка — дати в `component-registry.md` |
| Команда відповіла на відкрите питання | перенести відповідь у «Рішення» компонента, прибрати з питань, коміт |

## Цикл вивчення компонента

0. **Свіжі токени** (правило 0, `token-studio.md` → Свіжість експорту). Без них таблиця токенів описуватиме вже змінені значення. Якщо архіву немає — працювати з останнім експортом і записати його дату в «Мета знімка».
1. **Знайти компонент.** Посилання → `nodeId`; або назва → сторінка `↳ <Name>` → Section → набір. ID набору (або наборів) — у реєстр.
2. **Знімок.** Завантажити скіл `figma-use`, виконати `scripts/snapshot-component.js` через `use_figma` (read-only), підставивши ID. Результат зберегти **як є** у `snapshots/<component>.json` (kebab-case, однина: `anchor.json`, `anchor-item.json`).
3. **Подивитися очима.** `get_screenshot` на Section: стани поруч, Inverted, MB і XON (якщо режими показані). Звідси — «характер».
4. **Diff з минулим разом.** `python3 scripts/snapshot-diff.py snapshots/<component>.json` — порівнює робочий файл з останнім комітом. Перший раз diff порожній — це нормально.
5. **Вивчити й записати.** `python3 scripts/snapshot-diff.py --summary snapshots/<component>.json` дає осі варіантів, матрицю станів, токени по шарах, текстові стилі, вкладені інстанси. З цього і скриншота — оновити `references/components/<component>.md` за шаблоном `components/_template.md`. Значення токенів MB / XON — з `tokens/system/`.
6. **Звірити з правилами.** Пройти `definition-of-done.md` по знімку. Кожен ❌ — рядок у «Відхилення від правил» компонента, **не правка**. Якщо одне й те саме відхилення з'являється в кількох освіжених компонентах — імовірно, це нове рішення команди: спитати, чи оновити правило.
7. **Реєстр.** Рядок у `component-registry.md`: статус, дата вивчення, дата експорту токенів, ID, кількість варіантів.
8. **Журнал і коміт.** Запис у журнал `SKILL.md`; коміт у `main`: `learn(<component>): <що вивчено / що змінилось>`. Знімок, `.md` і реєстр — одним комітом, щоб наступний diff був чесним.
9. **Відповідь команді — коротко:** що вивчено, що змінилось від минулого разу (з diff), відхилення від правил, питання. 3–8 рядків.

## Що таке «характер» компонента

Те, чого не видно зі структури шарів:
- **Роль і місце:** де живе (картка, хедер, форма), на якому фоні, поруч з чим.
- **Поведінка:** що змінюється між станами (колір, обведення, тінь, розмір), що лишається.
- **Inverted:** які саме частини міняють колір.
- **MB vs XON:** чим бренди відрізняються (радіус, контраст, світлий/темний продукт).
- **Щільність і масштаб:** розміри, які є і яких немає (lg/md/sm), гнучкість ширини (HUG/FILL), переноси тексту.
- **Композиція:** які інші компоненти ДС всередині (instance), що конфігурується слотами/swap.
- **Межі:** що компонент свідомо НЕ вміє (наприклад, «без іконки праворуч»).

## Статуси в реєстрі

| Статус | Значення |
|---|---|
| `Ready for dev` | еталон, позначений командою |
| `Learned` | вивчено; знімок і `.md` відповідають файлу на дату вивчення |
| `Changed` | команда повідомила про зміни або diff їх показав — ще не вивчено заново |
| `In progress (team)` | команда зараз переробляє — не вивчати, поки не скажуть |
| `Rebuilt — review` | перескладено, чекає ревʼю команди |
| `Not started` | ще не вивчали |

Компонент вважається `Learned`, коли: є знімок; `.md` має всі розділи шаблону; токени звірено з актуальним експортом; відкриті питання або закриті, або явно винесені.

## Чого не робити
- Не змінювати нічого у Figma (жодних записів через `use_figma`).
- Не переписувати старі рішення в `.md` — нові додаються в кінець «Рішень»; скасоване закреслюється (`~~…~~ — скасовано: …`), як в `anchor.md`.
- Не видаляти старий знімок вручну — історія живе в git.
- Не робити висновок «стан відсутній = помилка» без DoD: стани інтерактивних компонентів — мінімум `Default | Hover | Active/Selected | Disabled`, неінтерактивним вони не потрібні.
